# 에이전틱 워크플로우 설계 패턴 실전 가이드

> 오케스트레이터-워커, 병렬 탐색, 반성 루프까지 — 코딩 자동화에 쓸 수 있는 6가지 패턴과 실제 Claude Code 적용법

## 이 가이드에서 다루는 것

- 에이전틱 워크플로우에서 자주 쓰이는 6가지 설계 패턴
- 각 패턴이 어떤 상황에 맞는지 판단 기준
- Claude Code 서브에이전트로 패턴을 구현하는 실제 프롬프트

## 패턴 개요

| 패턴 | 핵심 구조 | 적합한 상황 |
|------|-----------|-------------|
| 1. 프롬프트 체이닝 | 단계별 직렬 처리 | 순서가 정해진 다단계 작업 |
| 2. 오케스트레이터-워커 | 중앙 관리 + 서브에이전트 | 동적 태스크 분해 |
| 3. 병렬 탐색 | 여러 에이전트 동시 실행 | 대규모 코드베이스 분석 |
| 4. 반성 루프 | 생성 → 비평 → 개선 | 코드 품질 검증 |
| 5. 평가자-최적화 | 목표 기반 반복 | 테스트 통과까지 자동화 |
| 6. 전문가 라우팅 | 도메인별 에이전트 배정 | 이종 기술 스택 프로젝트 |

---

## 패턴 1: 프롬프트 체이닝

가장 기본적인 패턴. 이전 단계의 출력이 다음 단계의 입력이 됩니다.

### 언제 쓰는가

- 작업 순서가 명확하게 정해진 경우
- 중간 결과를 사람이 검토해야 하는 경우
- 각 단계의 컨텍스트가 독립적인 경우

### 구현 예시

```
[1단계] 프롬프트: "authentication 모듈의 구조를 분석하고, 현재 설계의 문제점을 정리해."
[2단계] 프롬프트: "앞 분석 결과를 바탕으로 개선 방안 3가지를 제안해."
[3단계] 프롬프트: "두 번째 방안을 코드로 구현해."
```

각 단계를 한 턴에 몰아넣으면 중간 검토가 불가능합니다. 명확한 전달이 필요한 단계는 나누는 것이 낫습니다.

---

## 패턴 2: 오케스트레이터-워커

중앙 오케스트레이터가 태스크를 분석하고, 각 서브에이전트(워커)에게 할당합니다. Claude Code에서는 `Task`를 통해 직접 구현합니다.

### 언제 쓰는가

- 작업 범위를 미리 정의하기 어려운 경우
- 서브태스크 간 의존성이 복잡한 경우
- 동적으로 에이전트 수를 조절해야 하는 경우

### 구현 예시

```
[오케스트레이터 프롬프트]
다음 리팩터링 작업을 분석하고 서브에이전트 3개로 나눠 실행해.

작업: 레거시 Express API를 타입스크립트로 마이그레이션

각 에이전트는 아래를 담당해:
- Agent 1: routes/ 디렉토리 분석 + 타입 정의 초안
- Agent 2: middleware/ 타입 추가
- Agent 3: services/ 비즈니스 로직 마이그레이션

각 에이전트의 결과를 수집한 후, 의존성 충돌 여부를 검토해.
```

### 주의점

오케스트레이터가 결과를 수집하는 단계에서 컨텍스트 윈도우 초과가 생길 수 있습니다. 워커에게는 요약된 결과만 반환하도록 지시하세요.

---

## 패턴 3: 병렬 탐색

여러 에이전트가 동시에 서로 다른 영역을 탐색합니다. 대규모 코드베이스 분석에서 시간을 크게 줄일 수 있습니다.

### 언제 쓰는가

- 코드베이스 전체를 빠르게 파악해야 할 때
- 독립적인 모듈을 동시에 수정해야 할 때
- 버그 원인을 여러 가능성으로 나눠 탐색할 때

### 구현 예시

```
다음 작업을 4개의 서브에이전트로 병렬 실행해.

각 에이전트는 서로 다른 디렉토리를 담당:
- Agent 1: src/api/ — REST 엔드포인트 목록과 입출력 타입 정리
- Agent 2: src/services/ — 비즈니스 로직 의존성 맵 작성
- Agent 3: src/models/ — 데이터 모델과 관계 정리
- Agent 4: src/utils/ — 공통 유틸리티 함수 목록과 사용처

모든 에이전트가 완료된 후 결과를 통합해 전체 아키텍처 요약을 작성해.
```

### 결과 통합 팁

병렬 탐색의 병목은 결과 통합 단계입니다. 각 에이전트에게 "JSON 형식으로 결과를 반환할 것"을 명시하면 통합이 쉬워집니다.

---

## 패턴 4: 반성 루프

에이전트가 자신의 출력을 스스로 비평하고 개선합니다. 코드 품질을 높이는 데 효과적입니다.

### 언제 쓰는가

- 첫 번째 출력의 품질이 불안정할 때
- 특정 기준(보안, 성능)을 반드시 충족해야 할 때
- 사람 리뷰 전에 자동으로 품질을 높이고 싶을 때

### 구현 예시

```
[생성]
JWT 인증 미들웨어를 작성해. Express + TypeScript 기준.

[비평]
방금 작성한 코드를 다음 기준으로 검토해:
1. OWASP Top 10 취약점 해당 여부
2. 토큰 만료 처리 누락 여부
3. 에러 메시지에 민감 정보 포함 여부

문제가 있으면 구체적으로 지적해.

[개선]
비평에서 지적된 문제를 수정한 최종 코드를 작성해.
```

### 루프 횟수 제한

반성 루프는 최대 2~3회로 제한하세요. 무한 루프는 API 비용을 급증시키고, 오히려 과도한 수정으로 이어질 수 있습니다.

---

## 패턴 5: 평가자-최적화

테스트 통과, 타입 체크 통과 등 명확한 목표를 기준으로 에이전트가 반복 개선합니다.

### 언제 쓰는가

- 단위 테스트가 이미 있고, 코드가 이를 통과해야 할 때
- 타입 에러나 린트 에러를 자동으로 해결해야 할 때
- 성능 벤치마크 기준이 있는 경우

### 구현 예시

```
다음 작업을 수행해. 테스트가 모두 통과할 때까지 반복해.

1. src/auth/jwt.ts 파일을 수정해 아래 테스트를 통과시켜.
2. 수정 후 `npm run test src/auth/jwt.test.ts` 를 실행해.
3. 실패한 테스트가 있으면 원인을 분석하고 코드를 수정해.
4. 모든 테스트가 통과하면 완료로 표시해.

최대 5회 반복. 5회 후에도 실패하면 실패 원인 요약을 제공해.
```

### 종료 조건 명시

"모든 테스트 통과"처럼 명확한 종료 조건을 반드시 지정하세요. 종료 조건이 없으면 에이전트가 루프를 스스로 종료하지 못합니다.

---

## 패턴 6: 전문가 라우팅

작업 유형에 따라 다른 전문 에이전트에게 라우팅합니다. 이종 기술 스택이 섞인 프로젝트에 유용합니다.

### 언제 쓰는가

- 프론트엔드, 백엔드, 인프라가 한 작업에 섞여 있을 때
- 각 도메인마다 다른 CLAUDE.md 규칙을 적용해야 할 때
- 코드 리뷰와 보안 감사를 별도 에이전트로 처리하고 싶을 때

### 구현 예시

```
다음 PR을 리뷰해. 아래 두 에이전트를 순서대로 실행해.

- Security Agent: 인증, 권한, 입력 검증 관련 취약점만 집중 리뷰
  → 결과: 심각/중간/낮음 등급의 보안 이슈 목록

- Performance Agent: N+1 쿼리, 불필요한 API 호출, 메모리 누수 리뷰
  → 결과: 성능 개선 권고사항 목록

두 에이전트의 결과를 통합해 최종 리뷰 코멘트를 작성해.
```

---

## 패턴 선택 기준

```
작업이 순서가 명확한가?
  → Yes: 프롬프트 체이닝
  → No: 아래로 진행

작업 범위가 실행 전에 확정되는가?
  → No: 오케스트레이터-워커

탐색할 영역이 독립적인가?
  → Yes: 병렬 탐색

품질 기준을 자동으로 검증할 수 있는가?
  → 코드 기준 (테스트/타입): 평가자-최적화
  → 정성적 기준: 반성 루프

도메인별 전문성이 필요한가?
  → Yes: 전문가 라우팅
```

## 자주 생기는 실수

| 실수 | 결과 | 대안 |
|------|------|------|
| 서브에이전트에게 전체 컨텍스트 전달 | 컨텍스트 초과 | 필요한 정보만 요약해서 전달 |
| 루프 종료 조건 생략 | 무한 반복 | 명확한 종료 조건 + 최대 반복 횟수 지정 |
| 병렬 에이전트 간 파일 충돌 | 코드 덮어쓰기 | 에이전트마다 작업 범위(디렉토리/파일) 명시 |
| 오케스트레이터에 모든 워커 결과 수집 | 컨텍스트 폭발 | 워커는 요약 결과만 반환 |
| 반성 루프 횟수 미지정 | API 비용 폭증 | 최대 3회로 제한 |

---

## 실전 조합 예시: 코드베이스 리팩터링

실제 작업에서는 패턴을 조합해서 씁니다.

```
[1단계 — 병렬 탐색]
4개 에이전트로 코드베이스 전체를 탐색해 기술 부채 목록 작성

[2단계 — 오케스트레이터-워커]
우선순위 높은 부채 3개를 각 에이전트에게 할당해 동시 수정

[3단계 — 평가자-최적화]
수정된 코드에 대해 전체 테스트 실행, 실패하면 해당 에이전트가 재수정

[4단계 — 반성 루프]
통합된 최종 코드를 코드 리뷰 기준으로 1회 비평 후 개선
```
