# 하네스 엔지니어링 실전 가이드 2026 — 프롬프트 대신 환경을 설계하는 AI 코딩의 새 패러다임

> 2022년 프롬프트 엔지니어링, 2025년 컨텍스트 엔지니어링, 그리고 2026년 하네스 엔지니어링 — AI 코딩 에이전트를 안정적으로 작동시키는 핵심이 바뀌었습니다.

---

## 왜 지금 하네스 엔지니어링인가

프롬프트를 아무리 정교하게 만들어도 에이전트는 여전히 실수를 반복합니다. 맥락을 잘 채워줘도 비결정적 출력은 피하기 어렵습니다.

2026년, 가장 앞서가는 팀들은 다른 방식으로 접근하고 있습니다. **에이전트에게 무엇을 하라고 지시하는 대신, 에이전트가 일하는 환경 자체를 설계하는 것**입니다.

이 접근법이 하네스 엔지니어링(Harness Engineering)입니다.

핵심 명제는 간단합니다:

> "에이전트는 어렵지 않다. 하네스가 어렵다." — OpenAI, Anthropic 공동 연구 (2026)

---

## 하네스의 두 축: 가이드와 센서

하네스는 두 가지 요소로 구성됩니다.

### 가이드 (Guides) — 사전 조향

가이드는 에이전트가 행동하기 **전에** 올바른 방향으로 이끄는 장치입니다.

| 가이드 유형 | 예시 | 효과 |
|------------|------|------|
| 컨텍스트 파일 | `CLAUDE.md`, `AGENTS.md` | 프로젝트 규칙, 디렉토리 구조 주입 |
| 아키텍처 문서 | ADR, 설계 결정 기록 | 허용/금지 패턴 명시 |
| 부트스트랩 스크립트 | 환경 초기화 | 첫 행동 전 컨텍스트 완성 |
| 예시 코드 | 패턴 레퍼런스 | "좋은 코드"의 정의를 코드로 전달 |

가이드는 에이전트가 처음부터 좋은 결과를 낼 확률을 높입니다.

### 센서 (Sensors) — 사후 수정

센서는 에이전트가 행동한 **후에** 결과를 관찰하고 자기수정 신호를 생성합니다.

| 센서 유형 | 예시 | 신호 품질 |
|----------|------|----------|
| 타입 체커 | TypeScript 컴파일러 | 즉각적, 정확 |
| 린터 | ESLint, Ruff | 빠름, 커스터마이즈 가능 |
| 테스트 | Jest, pytest | 통합적, 행동 검증 |
| E2E 테스트 | Playwright | 실제 사용자 관점 |
| LLM 심판 | Claude Code Review Agent | 의미론적 검증 |

센서가 생성하는 신호는 **LLM이 소비하기 좋은 형태**일수록 효과적입니다. 단순한 에러 코드보다 "왜 틀렸고, 어떻게 고쳐야 하는지"를 담은 커스텀 린터 메시지가 에이전트의 자기수정 성공률을 크게 높입니다.

## 실전 하네스 구축 4단계

### Step 1: CLAUDE.md / AGENTS.md 작성

가장 먼저 해야 할 일은 에이전트에게 프로젝트의 세계관을 전달하는 파일을 만드는 것입니다.

```markdown
# CLAUDE.md

## 프로젝트 개요
Next.js 15 + TypeScript + Prisma 기반 SaaS 플랫폼

## 핵심 규칙
- 모든 컴포넌트는 `src/components/` 에 위치
- API 라우트는 `src/app/api/` 아래에만 생성
- 직접 DB 쿼리 금지 — 반드시 `src/lib/db/` 레이어 통해 접근
- `any` 타입 사용 금지

## 테스트 명령어
- 단위 테스트: `pnpm test`
- E2E 테스트: `pnpm test:e2e`
- 타입 체크: `pnpm typecheck`

## 완료 기준
변경사항은 반드시 위 세 가지를 모두 통과해야 완료로 간주
```

**좋은 CLAUDE.md의 특징:**
- 금지 사항을 명확히 기술 ("절대 X하지 말 것")
- 완료 기준(Definition of Done)을 수치로 제시
- 자주 실수하는 패턴을 예시와 함께 포함

### Step 2: 피드백 루프 설정

최소 유효 하네스는 이 루프입니다:

```bash
# Claude Code에게 지시하는 방식
"기능 구현 후 반드시 아래 순서로 실행하고, 실패하면 고칠 것:
1. pnpm typecheck
2. pnpm lint
3. pnpm test
모두 통과해야 완료입니다."
```

Claude Code Hooks로 자동화하면 더 탄탄합니다:

```json
// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "pnpm typecheck 2>&1 | head -20"
          }
        ]
      }
    ]
  }
}
```

파일을 수정할 때마다 타입 체커가 즉시 실행되고, 에러가 있으면 에이전트가 다음 행동 전에 수정 신호를 받습니다.

### Step 3: 아키텍처 가드레일 추가

에이전트가 가장 많이 위반하는 패턴은 아키텍처 경계입니다. 린터로 강제할 수 있습니다:

```javascript
// eslint.config.js — 커스텀 아키텍처 규칙
export default [
  {
    rules: {
      // 컴포넌트에서 직접 DB 접근 금지
      "no-restricted-imports": [
        "error",
        {
          paths: [
            {
              name: "@prisma/client",
              message: "DB는 src/lib/db/ 레이어를 통해서만 접근하세요."
            }
          ]
        }
      ]
    }
  }
]
```

**핵심:** 에러 메시지에 "어떻게 고쳐야 하는지"를 포함시키면 에이전트가 이 신호를 프롬프트처럼 소비합니다.

### Step 4: 엔트로피 방지 에이전트

프로젝트가 커질수록 규칙이 지켜지지 않는 영역이 생깁니다. 주기적으로 실행되는 "청소 에이전트"가 이를 막습니다:

```bash
# 주간 일관성 검사 스크립트
#!/bin/bash

echo "=== 아키텍처 일관성 검사 ==="
pnpm lint --max-warnings=0

echo "=== 문서 동기화 검사 ==="
# CLAUDE.md에 명시된 경로가 실제로 존재하는지 확인
node scripts/check-claude-md-paths.js

echo "=== 미사용 exports 검사 ==="
pnpm ts-unused-exports tsconfig.json
```

## 하네스 강도 스펙트럼

모든 프로젝트에 최대 강도의 하네스가 필요한 건 아닙니다.

| 단계 | 구성 | 적합한 상황 |
|------|------|-----------|
| **Level 1** | CLAUDE.md + 기본 테스트 루프 | 개인 프로젝트, 탐색적 작업 |
| **Level 2** | + PostToolUse Hooks + ESLint | 팀 단위 기능 개발 |
| **Level 3** | + 아키텍처 린터 + E2E | 프로덕션 서비스 |
| **Level 4** | + LLM 심판 + 자동 엔트로피 방지 | 고위험 도메인 (결제, 인증) |

Level 1에서 시작해서 에이전트가 반복하는 실수 패턴이 보일 때 단계를 올리세요.

## 실패에서 배우는 하네스 개선 루프

하네스 엔지니어링의 핵심 사이클입니다:

```
에이전트 실수 발견
       ↓
"왜 이런 실수를 했는가?"
       ↓
가이드 부족? → CLAUDE.md 업데이트
센서 부족?  → 린터/테스트 추가
       ↓
같은 실수 재발 방지 확인
```

이 루프가 쌓이면 에이전트의 신뢰도가 누적적으로 향상됩니다.

## 컴퓨터 제어 vs. 추론 제어

하네스의 센서는 두 종류로 나뉩니다:

**결정론적 센서** (빠르고 정확)
- 타입 체커, 린터, 테스트
- 실행 속도: 밀리초~수초
- 거짓 양성 없음

**확률론적 센서** (의미론적 검증)
- LLM 기반 코드 리뷰, 보안 분석
- 실행 속도: 수초~분
- 더 깊은 맥락 이해 가능

두 종류를 조합할 때 가장 효과적입니다. 결정론적 센서로 명확한 오류를 먼저 잡고, 확률론적 센서로 "형식은 맞지만 의도에 맞지 않는" 코드를 걸러냅니다.

## 체크리스트

하네스가 충분한지 확인하는 기준입니다:

- [ ] 에이전트가 프로젝트 시작 전 CLAUDE.md를 읽고 있는가?
- [ ] 코드 수정 후 타입 체크와 린트가 자동으로 실행되는가?
- [ ] 에러 메시지에 수정 방법이 포함되어 있는가?
- [ ] 에이전트가 반복하는 실수 패턴이 기록되어 있는가?
- [ ] 아키텍처 경계 위반이 자동으로 감지되는가?
- [ ] 주기적으로 전체 일관성을 점검하는 루틴이 있는가?
