# AI 코딩 에이전트 자율성 5단계 가이드 2026 — 어떤 도구를 언제 써야 하는가

> "AI 코딩에 활용한다"는 말은 너무 많은 의미를 담고 있습니다. 인라인 자동완성부터 PR을 직접 올리는 자율 에이전트까지 — 각 도구의 특성과 실패 패턴은 전혀 다릅니다.

## 왜 단계 구분이 필요한가

팀에 "AI 코딩 도구 써보세요"라고 하면 어떻게 됩니까? 누군가는 Copilot 자동완성, 누군가는 Claude Code와 채팅, 누군가는 배경 에이전트에 작업을 넘깁니다.

결과가 들쭉날쭉한 건 도구 탓이 아닙니다. **잘못된 도구를 잘못된 상황에 쓰기 때문**입니다.

2026년 3월 Swarmia가 발표한 5단계 자율성 분류 체계는 이 문제를 해결합니다. 기준은 하나입니다: **에이전트가 피드백을 요청하기 전에 얼마나 자율적으로 작업하는가?**

높은 단계가 항상 좋은 건 아닙니다. 인턴에게 CEO 역할을 맡기면 재앙입니다. 전문가를 심부름꾼으로 쓰면 낭비입니다.

---

## Level 1: 어시스티브(Assistive) — 자동완성과 단일 파일 편집

자율성이 아닌 **편의성**이 핵심입니다.

열려 있는 파일 안에서만 작동합니다. 인라인 제안, 단일 파일 리팩터링, 빠른 수정. 창을 닫으면 아무것도 기억하지 않습니다. ChatGPT와 대화하는 것도 여기 속합니다 — 맥락을 직접 관리하는 한.

### 이럴 때 쓰세요

| 상황 | 이유 |
|------|------|
| 단일 파일 작업 | 설정 비용 제로 |
| 모든 변경에 직접 개입하고 싶을 때 | 완전한 제어 |
| 낯선 코드베이스 파악 중 | 맥락 없이 시작 가능 |

### 이럴 때 쓰지 마세요

여러 파일에 걸친 문제, 넓은 컨텍스트가 필요한 작업. Level 1은 못 봅니다, 볼 수가 없습니다.

### 측정 지표

- 도입률: 라이선스 보유 팀원 중 실제 사용 비율
- 수락률: 제안된 코드 중 실제 채택 비율
- 비활성화율: 끈 이유가 무엇인가

---

## Level 2: 대화형(Conversational) — 멀티 파일, 인터랙티브 코딩

**읽어준 문서를 기억하는 페어 프로그래밍 파트너**와 비슷합니다.

코드베이스를 직접 알지는 못합니다. AGENTS.md에 적힌 것, 직접 가리켜 준 파일만 압니다. 여러 파일에 걸친 수정, 테스트 실행, 코드 리뷰 — 하지만 방향은 항상 사람이 잡습니다.

실제로는 이렇게 씁니다:
- 에이전트에 접근법 계획 요청 → 검토 → 진행
- 멀티 파일 편집을 하나씩 검토하며 수락 또는 거절
- 복잡한 문제를 작은 단계로 나누어 자주 체크포인트

Anthropic 자체 엔지니어들도 작업의 60%에 AI를 활용하지만, 80~100% 작업에 인간 감독을 유지한다고 보고했습니다. 무게 중심은 여전히 협력적 대화형에 있습니다.

### 이럴 때 쓰세요

```bash
# 예시: 복잡한 기능 구현
claude "auth 모듈에 OAuth2 PKCE 플로우 추가해줘.
현재 구조는 src/auth/, 새 엔드포인트는 /api/auth/callback"

# 계획 검토 후 계속 진행
```

| 상황 | 이유 |
|------|------|
| 판단이 필요한 멀티 파일 작업 | 방향을 직접 조율 가능 |
| 복잡한 기능, 아키텍처 결정 | 결과가 모호할 때 |
| 사전에 "완료"를 명확히 정의하기 어려울 때 | 유연한 피드백 루프 |

### 이럴 때 쓰지 마세요

작업이 이미 명확히 정의된 경우. 그건 Level 3의 영역입니다.

---

## Level 3: 태스크 에이전트(Task Agent) — PR을 혼자 올리는 에이전트

**에이전트에 작업을 맡기고 돌아오면 PR이 올라와 있는** 단계입니다.

확인 기준: 노트북 없이 폰으로 PR을 만들 수 있나? 된다면 Level 3입니다.

```bash
# 실전 예시 1: Slack에서 Cursor 태깅
@Cursor auth 페이지에서 Google SSO 버튼 클릭 시 404 발생, 수정해줘

# 실전 예시 2: GitHub Issue에 Copilot 할당
# → 에이전트가 레포 클론 → 작업 → CI 실행 → PR 생성 → 리뷰 대기

# 실전 예시 3: Claude Code GitHub Actions
# PR 코멘트에 @claude 멘션 → 자동 수정 PR 생성
```

### 좋은 Level 3 작업

| 유형 | 예시 |
|------|------|
| 명확한 버그 수정 | "로그인 시 500 에러, 재현 단계 첨부" |
| 의존성 업데이트 | npm 패키지 보안 패치 |
| 완전히 명세된 기능 | 스펙 문서가 있는 새 API 엔드포인트 |
| 코드 포맷팅/정리 | ESLint 규칙 일괄 적용 |

### 주의 사항

에이전트는 낙관적입니다. 뭔가 만들어냅니다, 해야 하는지 여부와 관계없이. CI가 약하면 문제가 그냥 통과합니다.

```yaml
# CI 최소 요구사항 (Level 3 도입 전 확인)
on: [pull_request]
jobs:
  quality-gate:
    steps:
      - run: npm test
      - run: npm run type-check
      - run: npm run lint
```

### 측정 지표

- 머지율: 에이전트 PR 중 실제 머지 비율
- 배치 크기: 에이전트 PR당 변경 파일 수 (작을수록 리뷰 부담 낮음)
- PR당 리뷰 시간: 에이전트 PR과 사람 PR 비교

## Level 4: 자율 팀원(Autonomous Teammate) — 작업을 스스로 찾는 에이전트

**누가 할당하지 않아도 작업을 찾아서 처리**합니다.

이미 친숙한 예시: Dependabot. 의존성을 모니터링하고 outdated/취약 패키지를 발견하면 PR을 올립니다. 차이점은 LLM 에이전트가 규칙이 아닌 판단으로 작동한다는 것.

### 실제 사례

**Uber FlakyGuard:**
- 매일 플래키 테스트 보고서를 처리
- 6개월간 1,115건 처리 → 798건 재현 → 380건 수정 생성 → 197건 머지 성공
- 아무도 할당하지 않아도 작동

**GitHub Agentic Workflows:**
```yaml
# Daily Test Improver
schedule: "0 2 * * *"  # 매일 새벽 2시
tasks:
  - analyze_test_coverage
  - identify_undertested_areas
  - generate_tests
  - open_pr_if_coverage_improved

# Daily Documentation Updater
tasks:
  - detect_merged_prs_last_24h
  - update_affected_docs
  - open_pr_with_changes
```

**Cursor Automations:**
Linear 이슈 생성, PR 머지, PagerDuty 인시던트 — 이벤트 트리거 또는 스케줄로 에이전트가 자동 실행.

### 이럴 때 쓰세요

아무도 하기 싫어하지만 예측 가능하게 반복되는 작업. 협의 비용이 실제 작업 비용보다 높을 때.

- 플래키 테스트 수정
- 문서 최신화
- 의존성 보안 패치
- 코드 스타일 일관성 유지

### 이럴 때 쓰지 마세요

작업 유형이 다양해서 안정적인 목표를 정의할 수 없는 경우. PR 리뷰 부담이 절약 시간을 초과하면 역효과.

---

## Level 5: 에이전트 연쇄(Agentic Avalanche) — 멀티 에이전트 오케스트레이션

**대부분의 팀은 아직 여기가 아닙니다**, LinkedIn에 어떻게 보이든.

여러 에이전트가 협력합니다. 오케스트레이터가 서브에이전트를 생성하고, 에이전트들이 병렬로 작업하며, 인간 감독은 최소화.

### 실제 사례: Cursor FastRender

```
아키텍처:
Planner 에이전트 → 목표 분해
Worker 에이전트 (최대 2,000개 병렬) → 격리된 환경에서 실행
Judge 에이전트 → 품질 평가 및 계속 여부 결정

규모:
- 수조 토큰 소비
- 100만 줄 이상 코드 생성
- 1,000개 파일, 30,000개 커밋
- 거의 1주일간 실행
```

### 설계 원칙

| 항목 | 내용 |
|------|------|
| 신뢰 경계 | 서브에이전트가 자율 결정 가능한 범위 vs. 에스컬레이션 필요 범위 |
| 인간 감독 위치 | 서브에이전트가 자유롭게 실행해도 오케스트레이터 레벨에서 누군가 모니터링 |
| 디버깅 계획 | 멀티 에이전트 장애는 단일 에이전트 장애보다 근본적으로 진단이 어려움 |

### 이럴 때 고려

대규모 병렬화가 진정으로 필요하고, Level 3과 4를 이미 잘 운영 중일 때. 복잡도 비용이 상당하므로 문제가 그것을 정당화해야 합니다.

## 올바른 단계 선택법

작업을 시작하기 전에 한 가지 질문을 던지세요:

> **"완료"가 어떤 모습인지 한 문장으로 명확히 표현할 수 있는가?**

```
YES → 에이전트가 혼자 처리 가능 (Level 3+)
       └ 반복적인가? → Level 4
       └ 대규모 병렬화 필요? → Level 5

NO → 사람이 루프에 있어야 함 (Level 2)
     └ 단일 파일이고 지금 당장인가? → Level 1
```

### 팀별 흔한 병목

대부분의 팀은 Level 2~3 사이 어딘가에서 천장을 만납니다. 도구 문제가 아닙니다. **얼마나 의도적으로 쓰는지**의 문제입니다.

| 증상 | 원인 | 해결 |
|------|------|------|
| 에이전트 PR 머지율이 낮음 | 작업이 너무 모호함 | Level 2로 내려가서 명세 먼저 |
| 리뷰 시간이 늘어남 | 에이전트 PR이 너무 큼 | 배치 크기 줄이기, 명세 구체화 |
| 도구를 제대로 안 씀 | 어떤 상황에 쓸지 불명확 | 단계 기준 명확화, 사례 공유 |
| Level 3 실패 잦음 | CI가 약함 | 품질 게이트 강화 먼저 |
